## 一句话题目定义

把题目压缩成以下结构：

> 面向“对象/场景”中的“具体问题”，采用“方法或机制”，构建“可交付成果”，并通过“指标与评价方式”验证其在该场景下相对“基线”的效果。

每项都必须具体到可以检查。例如：

- “面向课程作业的智能平台”不可验收；
- “面向短文本作业的自动评分与反馈系统，在固定评分标准下，用与人工评分的一致性证明其可用性”可以进入设计阶段。

同时记录：

- 研究对象与适用范围；
- 核心问题；
- 当前做法及不足；
- 拟采用方法；
- 最终成果；
- 评价数据和指标；
- 明确不研究的边界。

## 可行性审查

用“阻断项 / 高成本项 / 可接受项”分类，而不是只给总体评分。

| 维度 | 必须回答 | 不合格信号 |
|---|---|---|
| 数据 | 数据从哪来、是否可合法使用、多久能拿到 | 只写“后续收集” |
| 被试/现场 | 是否需伦理审批、招募或场地许可 | 时间不确定且实验依赖它 |
| 设备与算力 | 关键实验是否能在现有资源完成 | 只能依赖无法申请的资源 |
| 技术 | 核心难点是否有已知可行路径 | 核心难点本身尚未验证 |
| 评价 | 是否存在可比较的基线和指标 | 只能展示结果，无法判断好坏 |
| 时间 | 最晚何时必须拿到第一组有效数据 | 实验被安排在全部开发之后 |
| 学术规范 | 引用、隐私、版权、工具使用要求 | 尚未核对学校或期刊规定 |

优先做“最可能推翻题目”的可行性验证。例如先取得 20 条真实样本、跑一次小规模基线，或做一次现场访谈；这比继续阅读几十篇泛泛相关的文章更能降低风险。

## 收缩题目

题目过大时，按以下顺序收缩：

1. 缩小场景或对象，但保留核心问题。
2. 缩小数据或输入类型，换取可验证性。
3. 保留一条核心方法，删除与它不形成对照的附属模块。
4. 把系统目标改为一个明确指标，例如准确性、响应时间、审核效率或用户理解度。
5. 把“通用方案”改为“在明确条件下有效的方案”。
6. 如果仍不可行，把工程系统降为案例研究，把评价重点转向设计过程与适用条件。

不要用“增加系统规模”掩盖研究问题缺失；也不要用“数据以后会很多”替代当前数据可得性证明。

## 文献检索与筛选

先写清楚检索协议：

- 核心概念及同义词；
- 数据来源；
- 时间范围与语言；
- 纳入标准；
- 排除标准；
- 检索日期；
- 筛选理由。

来源优先级取决于领域，通常包括同行评议论文、领域会议、权威综述、标准、正式技术报告和官方文档。二手博客可帮助定位线索，但不应单独支撑关键学术声明。

至少阅读：

- 2–3 篇领域综述，建立问题地图；
- 5–8 篇与当前问题最接近的方法论文；
- 2–3 个可比基线或公开数据；
- 必要的批判性研究，避免只收集支持当前方案的材料。

引用前核对标题、作者、年份、来源、DOI 或稳定链接。无法核验的文献标为待核验，不得写入正式参考文献。

## 证据矩阵与研究缺口

每篇核心文献填写：

| 字段 | 目的 |
|---|---|
| 研究问题 | 防止只摘录方法 |
| 数据/样本 | 判断结论适用范围 |
| 方法 | 与拟用方法比较 |
| 基线 | 判断结果是否公平可比 |
| 指标与结果 | 提取可复现结论 |
| 局限 | 推导研究缺口 |
| 对本课题的作用 | 决定是否真正相关 |

“研究缺口”只能从比较中推导，不能仅用“研究较少”作为理由。有效缺口可表现为：

- 已有方法在特定数据、成本或场景下失效；
- 两个相互矛盾的结果尚未解释；
- 评价指标缺失或不能反映真实需求；
- 方法需要难以获得的条件；
- 已有研究缺少可复现实验或公平基线。

把缺口转换为待验证假设，例如“在长尾类别上，方法的准确率会明显下降”，再说明如何检验。不要直接写成“因此我要提出一个更好的系统”。

## 开题表达的检查点

开题材料至少能回答：

1. 问题为什么真实存在，而不是作者主观认为？
2. 现有方案做到了什么，具体缺什么？
3. 本课题用什么方法补这个缺口？
4. 数据、资源和时间是否足够？
5. 什么结果会被视为成功或失败？
6. 如果核心方法失败，最小退路是什么？

开题不是承诺“结果一定显著更好”，而是说明问题有价值、路线可执行、评价可判定。
