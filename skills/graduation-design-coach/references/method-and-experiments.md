# 方法、实现与实验

## 目录

- 方法选择与论证
- 系统设计的最小闭环
- 评价协议
- 实现过程中的证据记录
- 负结果与返工

## 方法选择与论证

对每个主要方法选择记录：

| 候选方案 | 预期优势 | 成本/依赖 | 主要风险 | 选择或排除理由 |
|---|---|---|---|---|
| 基线方案 | 熟悉、可比较 |  | 无创新或效果不足 |  |
| 主方案 | 对应研究缺口 |  | 是否能在时间内验证 |  |
| 简化退路 | 快速得到证据 | 贡献较小 | 结论范围受限 |  |

方法复杂度必须由研究问题驱动。禁止仅因“更新”“更热门”而选择方法；也禁止为了显得完整同时加入多套互不关联的技术。

在正式构建前做一个技术验证：

- 数据能否被正确读入和标注；
- 核心算法或流程能否产生预期形态的输出；
- 评测指标能否计算；
- 至少一个基线是否可复现；
- 关键依赖是否可获得。

技术验证成功只表示路线可行，不等于方法有效。

## 系统设计的最小闭环

先用一条端到端链路证明系统能够产生可评价结果：

1. 真实或代表性输入；
2. 核心处理；
3. 可检查输出；
4. 记录与评价；
5. 能从日志回到对应输入和配置。

界面、权限、复杂后台和非核心扩展只有在支持验收或演示时才纳入主线。每个模块都应说明它支持哪个研究问题、实验或交付要求。

优先实现“窄而完整”的原型，而不是多个彼此独立的半成品。

## 评价协议

每条论文效果声明都应映射到一个可执行实验。实验计划至少包含：

- 要检验的假设；
- 数据及划分方式；
- 自变量和受控条件；
- 基线；
- 指标、方向和可接受阈值；
- 重复次数或样本量依据；
- 统计或不确定性分析方法；
- 结果文件位置；
- 失败标准或停止条件。

| 声明示例 | 需要的证据 |
|---|---|
| “系统可以完成任务” | 端到端案例与功能测试 |
| “方法比基线准确” | 同一数据、同一评价口径下的对照结果 |
| “模块 A 有贡献” | 去除/替换 A 的消融或对照实验 |
| “响应更快” | 同一负载、相同硬件和测量协议 |
| “用户更容易理解” | 明确定义的任务、量表和统计分析 |
| “在真实场景有效” | 代表性场景样本与外部效度讨论 |

不要用不同数据、不同指标或不同计算预算的结果直接下结论。无法公平比较时，明确缩小声明范围。

### 数据

记录数据来源、许可、采集/筛选过程、标签定义、缺失值、划分方法和潜在偏差。训练、验证、测试应有明确边界，防止泄漏或重复样本。

### 基线

基线应能代表“当前常见做法”或“无核心创新的对照”。至少选择一个有说服力且可复现的基线。基线太弱会让效果看起来更好，却无法支持研究贡献。

### 指标

为每个指标写清：

- 计算方式；
- 越大越好还是越小越好；
- 单位；
- 适用条件；
- 不分段或只报告均值的风险；
- 是否需要置信区间、方差或显著性检验。

### 预实验

在大规模实验前完成最小预实验：少量真实样本、一个主要基线、一个核心指标。预实验的用途是发现数据、流程或指标问题，不能直接作为最终证据，除非样本和协议足以支撑结论。

## 实现过程中的证据记录

每次正式运行保存：

- 代码版本或不可变快照；
- 数据版本；
- 配置、随机种子和环境信息；
- 运行命令；
- 原始输出；
- 清洗和汇总脚本；
- 最终图表对应的数据表。

建立运行日志，区分：

- 失败运行及失败原因；
- 调试运行；
- 可用于分析的正式运行。

不要覆盖唯一结果文件。图表必须有可追溯的数据源，不能只在演示软件中手工修改后保存截图。

## 负结果与返工

负结果不等于项目失败。判断顺序：

1. 数据与标签是否存在问题；
2. 基线或主方法是否实现公平；
3. 指标和统计是否解释正确；
4. 方法假设是否与场景不匹配；
5. 是否需要缩小声明或修改方法。

只有在排除实现错误和评价错误后，才能把负结果解释为方法局限。保留失败实验及其分析，因为“在何种条件下无效”本身可能是论文贡献。
