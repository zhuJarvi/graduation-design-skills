# 毕业设计独立审查

正式审查必须在隔离的子智能体上下文中完成。协调者可以准备材料和接收报告，但不能代替审查者得出结论。

## 硬性约束

- 正式审查必须使用子智能体，并使用 `fork_turns="none"`，不继承父级对话、作者分析、预期答案或以往审查结论。
- 协调者只向审查者提供冻结的审查包、审查模式、评价标准和输出路径。
- 审查者第一阶段只审查，不修改被审查文件，不与作者协商结论。
- 若当前环境没有可用的子智能体能力，停止正式审查并明确告知用户。可以把材料整理好，但不能把同上下文自查宣称为独立审查。
- 子智能体若只返回问候、泛泛确认或未读取审查包，视为启动失败。不得把它的回复当作审查结果。
- 协调者不得改写、降级、删除或私下关闭审查者的问题。对结论有异议时，只能补充证据并要求复审或独立仲裁。
- 审查、修复、复审是三个分离步骤。修复完成后必须核对新版本，旧报告不能自动用于新版本。

详细隔离与复审协议见 [references/protocol.md](references/protocol.md)。

## 角色识别

先判断当前角色：

- **协调者**：收到用户或毕业设计教练的审查请求。负责冻结材料、启动审查子智能体、接收报告和推动修复，不负责给出独立结论。
- **审查者**：收到明确写有“独立审查者”的任务。直接按指定模式完成审查，不得再启动新的审查子智能体，除非协调者明确要求仲裁。

如果角色不清，按协调者处理；不要在没有隔离的情况下直接开始审查。

## 模式路由

只读取当前模式需要的文件。

| 模式 | 使用场景 | 审查清单 |
|---|---|---|
| `formula` | 公式、统计模型、算法更新、约束、证明、近似、数值一致性 | [references/formula.md](references/formula.md) |
| `code` | 代码正确性、测试、复现、数据流、实验实现、安全风险 | [references/code.md](references/code.md) |
| `paper` | 整篇论文的贡献、证据、实验、图表、引用和规范 | [references/paper.md](references/paper.md) |

如果材料涉及多个模式，优先拆成独立审查，不要用一个笼统结论覆盖。论文审查不替代公式和代码审查。

## 协调者流程

1. **冻结范围**：确定审查类型、版本、必须审查的内容和明确不审查的内容。
2. **建立审查包**：使用对应 `assets/` 模板，将材料整理到独立审查目录。计算关键文件哈希；脱敏凭据、个人信息和受限数据。
3. **最小披露**：不提供作者的预期结论、已知缺陷、希望得到的评价、历史审查结果或“请重点证明没问题”之类引导。
4. **启动审查者**：使用 `spawn_agent`，设置 `fork_turns="none"`，任务名使用如 `formula_review_001`、`code_review_002`、`paper_review_003` 的形式。提示词模板见 [assets/reviewer-prompt.md](assets/reviewer-prompt.md)。启动后核对子智能体是否确认了具体审查包、模式、输出路径和禁止修改要求。
5. **等待报告**：要求审查者输出 `review-report.md` 和 `review-issue-log.csv`。审查者必须给出通过、有条件通过或不通过。若子智能体返回问候、说明工作区为空或没有生成文件，先发送一次包含精确绝对路径和输出要求的纠正任务；仍失败则停止并向用户报告，不得由协调者补写报告。
6. **结构核验**：运行 `scripts/audit_review_log.py` 检查问题表结构、未关闭 P0 和关闭证据，但不得自行改变问题等级或结论。
7. **交付作者**：把审查报告原样提供给作者，区分“必须修复”“需要决策”和“可接受风险”。
8. **修复后复审**：作者在独立步骤中修复。使用 `followup_task` 让原审查者核对新版本和差异，不重新解释原结论。
9. **争议仲裁**：只有对 P0 或结论存在实质分歧时，才启动新的无历史子智能体做仲裁。仲裁者接收双方证据和争议点，不接收预设仲裁结果。

审查窗口超过一次工作周期时，先向用户说明仍在等待；不要由协调者补写审查结论。

## 审查包

每个审查包至少包含：

- 审查编号、类型、日期和审查者独立性说明；
- 被审查版本的不可变快照或哈希；
- 研究问题和预期用途；
- 学校、导师或项目标准；
- 原始材料及位置；
- 明确排除或未覆盖的内容；
- 输出要求与结论门槛。

对应模板：

- `assets/formula-review-package.md`
- `assets/code-review-package.md`
- `assets/paper-review-package.md`
- `assets/review-report.md`
- `assets/review-issue-log.csv`

材料不全时不能给出“通过”。若缺失内容不阻断主路径，可给“有条件通过”并限定范围；若缺失核心证据，给“不通过”并说明需要什么。

## 审查者输出

审查者必须：

1. 先独立重建材料实际支持的声明；
2. 按领域清单核验关键步骤、实验或论证；
3. 记录问题和可定位证据；
4. 使用 P0、P1、P2 分级；
5. 给出有边界的结论；
6. 写明未审查内容和复审条件；
7. 把 `review-report.md` 与 `review-issue-log.csv` 写入审查目录。

P0 是结论失效或关键路径不可接受的阻断问题；P1 是可能改变结论、公平性、可复现性或答辩判断的重要问题；P2 是不影响核心结论的完整性和清晰度问题。

## 结论门槛

| 结论 | 要求 |
|---|---|
| 通过 | 无未关闭 P0/P1；关键路径已核验；剩余 P2 不影响提交 |
| 有条件通过 | 无未关闭 P0；剩余 P1 不影响核心贡献，并有负责人、截止时间和复审方式 |
| 不通过 | 有未关闭 P0，或核心材料缺失导致关键声明无法验证 |

问题表只有在 `resolution`、`verified_by` 和 `verification` 都有内容时才能标记 `closed`。P0 不得以 `accepted_risk` 代替关闭。

检查问题表：

```bash
python3 scripts/audit_review_log.py path/to/review-issue-log.csv --fail-on p1
```

## 完成标准

只有同时满足以下条件，审查任务才算完成：

- 由隔离审查者完成，而非协调者自查；
- 报告对应明确版本；
- 问题表可追踪；
- 结论与问题等级一致；
- 未审查范围已说明；
- 修复后的复审有证据，或明确标记为尚未完成。
